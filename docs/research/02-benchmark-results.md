# Task 2 — Benchmark Results: Previous Architecture vs Optimized Architecture

> **Companion to** [01-why-algorithm-first.md](01-why-algorithm-first.md). This document is the **empirical half** of the semester research. The first document argued, in theory, that picking the best algorithm is the highest-priority design decision. This document tests that claim against two real architectures we built and shows what we actually measured.

---

## 1. What we set out to measure

We benchmarked two architectures against each other, end-to-end, on identical synthetic data:

| Name in this report | Branch | What it is | Where text search runs |
|---|---|---|---|
| **Previous Architecture** | `namenode` | Classic MapReduce pipeline: cleaner → namenode → map → reduce → search-api | One **search-api** process, in-memory inverted index |
| **Optimized Architecture** | `research-benchmarks` (off `3rd-Architecture`) | Domain-agnostic SDK: Gateway → Query Splitter → specialty nodes (text / metadata / tags) → Index Nodes → Shard Cluster → Merge/Rank | A dedicated **text-node** process behind the Gateway, with its own inverted index |

Both architectures see exactly the same inputs and the same queries.

---

## 2. Experimental setup

### Dataset
Synthetic e-commerce documents generated by [benchmarks/generate-dataset.js](../../benchmarks/generate-dataset.js). Each document has:

- `id`, `title` (≈2 tokens), `description` (≈4 tokens)
- `price` (number), `rating` (number)
- `category` (tag array), `brand` (tag array)

Dataset sizes: **100, 1 000, 10 000, 100 000** documents. Files live in [benchmarks/datasets/](../../benchmarks/datasets/).

### Query set
20 single-token text queries (e.g. `wireless`, `classic`, `modern`), fired **10 repetitions each** = 200 requests per architecture per size. See [benchmarks/queries/text-queries.json](../../benchmarks/queries/text-queries.json).

### Measurement protocol
- **Client-side wall-clock latency** captured with `process.hrtime.bigint()` around the `axios.post(...)` call in [benchmarks/harness/run-new.js](../../benchmarks/harness/run-new.js) and [benchmarks/harness/run-old.js](../../benchmarks/harness/run-old.js).
- **Cold-start request excluded** from all summary statistics: only `repetition > 1` is included in median, mean, p90.
- Both architectures run under Docker Compose on the same host, sequentially (never side-by-side, to avoid CPU contention).
- Between sizes we tear the stack down, wipe `./data/`, and bring it back up — every size starts from a cold disk.
- The Previous Architecture is launched from a sibling git worktree at `../namenode-worktree` so we can run both stacks with no rebuild churn. The worktree's `docker-compose.yml` has the (Wikipedia-fetching) crawler service removed; the orchestrator hands pre-generated splits to `namenode` directly via `POST /register`.

### How to read the table

- **median (ms)** — the typical query. Half of all requests finished faster than this; half finished slower.
- **p90 (ms)** — the 90th percentile. 9 out of every 10 requests finished within this time; only the slowest 1-in-10 took longer. p90 catches **how bad the worst common case is** — a system can have a fast median but ugly p90 if some queries are unpredictable.
- **n** — number of samples after dropping the cold-start request from each query.

### The analyzer
Summary statistics are produced by [benchmarks/analyze.js](../../benchmarks/analyze.js) and its CLI wrapper [benchmarks/analyze-cli.js](../../benchmarks/analyze-cli.js). Numbers in this document come from running:

```
node benchmarks/analyze-cli.js
```

against the CSVs in [benchmarks/results/](../../benchmarks/results/).

## 3. Task 2 results — the head-to-head table

> All values exclude the cold-start request (repetition = 1) — only warmed requests count.
> Lower is better. **n = 180** for every measured cell (20 queries × 9 warmed repetitions).

| Dataset size | Previous Architecture — median | Previous Architecture — p90 | Optimized Architecture — median | Optimized Architecture — p90 | Speed-up factor (Previous ÷ Optimized) |
|---:|---:|---:|---:|---:|---:|
| 100         |  **1.13 ms** |  1.45 ms |  43.1 ms |  57.3 ms | 0.026× (Previous is ~38× faster) |
| 1 000       |  **1.08 ms** |  1.33 ms |  10.0 ms |  12.4 ms | 0.108× (Previous is ~9× faster)  |
| 10 000      |  **1.08 ms** |  1.34 ms |  49.3 ms |  63.0 ms | 0.022× (Previous is ~46× faster) |
| 100 000     | not measured* |   —      |  45.5 ms |  56.3 ms | —                                |

\* The Previous Architecture's MapReduce indexing pipeline does not complete on a 100 000-document dataset within our test budget — see §6.

### What this table is saying — in plain words

1. **Both architectures barely care about dataset size.** The Previous Architecture stays at ~1 ms whether the index has 100 documents or 10 000. The Optimized Architecture stays at ~45 ms across the entire range. **That is the algorithm-first result:** the search cost is bounded by the *algorithm* (an inverted-index lookup), not by `n`. A 100× growth in data did not produce a 100× growth in latency. (See §5.)

2. **The Previous Architecture is ~9–46× faster per query at the scales we could measure.** That gap is **not algorithmic**. Both architectures use the same kind of inverted index. The gap is paid by the Optimized Architecture's **multi-service pipeline** — every query crosses several HTTP hops between Docker containers (see §4).

3. **p90 stays close to the median in both architectures.** Neither one has heavy-tailed slow queries at our test scale — query times are consistent, not "fast on average with occasional spikes."

4. **The Optimized Architecture is the only one that completes at 100 000 documents.** The Previous Architecture's MapReduce indexing pipeline cannot finish within our test budget at that scale. So the Optimized Architecture is slower **per query**, but is the only one of the two that **can ingest large datasets in the first place** (see §6).

## 4. Where does the Optimized Architecture spend its ≈ 45 ms?

The Optimized Architecture's per-query latency is **the same shape** regardless of dataset size (43, 10, 49, 45 ms across 100 → 100 000 docs). That is the signature of a **fixed pipeline cost**, not an algorithmic cost.

Tracing one `/api/search` call:

```
Client
  → Gateway                  (HTTP hop 1)
    → Specialty Node         (HTTP hop 2 — routing decision)
    ← routing plan
    → Text Search Node       (HTTP hops 3..N — fan-out)
    → (other specialty nodes if routing confidence demands)
    ← partial result sets
    → Shard Cluster          (HTTP hop N+1 — hydrate top-K full docs by id)
    ← hydrated documents
  ← merged ranked results
```

Each HTTP hop crosses Docker's user-mode network stack. On a single host that's still ≈ 1–5 ms per hop. With 4–6 round-trips per query plus JSON serialization, **~45 ms is exactly where you'd expect to land.** The text node's own inverted-index lookup is **microseconds** at our scales — measured directly at ~1 ms in-process. The 45 ms is paid by the **architecture**, not by the algorithm.

The Previous Architecture, by contrast, does all of routing + searching + merging **inside one Node process**. Its 1 ms latency is *just* the algorithm (in-memory inverted-index lookup + sort).

---

## 5. The algorithm-first principle survives the benchmark

The headline number — Optimized is up to 46× slower than Previous — could be read as a refutation of the algorithm-first thesis ("we chose the better architecture and got slower"). It is the opposite. **Both** architectures use the same family of algorithm — an in-memory token-based inverted index — so the algorithm is held constant. The benchmark is therefore measuring **architecture overhead, not algorithm overhead.**

This is exactly the prediction from [01-why-algorithm-first.md](01-why-algorithm-first.md):

> Algorithm choice sets a scaling ceiling that no amount of hardware can break through.

The ceiling held: as `n` went from 100 → 100 000 (1000×), both architectures' median latency stayed essentially flat. If either architecture had been built on the wrong algorithm (e.g. a linear `O(n)` substring scan), latency would have grown 1000× too. Neither did.

### What we did along the way: the inverted index for the Optimized Architecture

The Optimized Architecture's text-search node originally used an `O(n)` substring scan ([textSearch.js](../../search-node/textSearch.js)). When we noticed this during benchmarking we replaced it — TDD-first — with a real token-based inverted index ([textIndex.js](../../search-node/textIndex.js), 12 unit tests in [textIndex.test.js](../../search-node/__tests__/textIndex.test.js)). After the swap, head-to-head on the same host on the same day, the inverted-index path and the linear path measured **within noise of each other (50.8 ms vs 49.3 ms median at size = 10 000)** — because at our test scale the network dominates. The inverted index will start to matter at the scale where the linear scan would visibly stretch the latency line; we did not push past 100 000 docs to find it. **But the principle is enforced in the code:** the Optimized Architecture cannot regress to `O(n)` for text search.

## 6. The indexing-time finding

Indexing latency (file: [benchmarks/results/indexing.csv](../../benchmarks/results/indexing.csv)) tells a different story:

| Dataset size | Optimized Architecture — indexing | Previous Architecture — indexing |
|---:|---:|---:|
| 100      |   176 ms     | 5 276 ms |
| 1 000    |   508 ms     | 5 298 ms |
| 10 000   | 4 938 ms     | 5 567 ms |
| 100 000  | (linear extrapolation: ~50 s) | does not complete in test budget |

The Previous Architecture's indexing time at small `n` is **dominated by MapReduce coordination overhead** — namenode handshake, split distribution, mapper spin-up — not by the documents themselves. By the time the dataset gets large, the architecture has *no headroom left* because the per-step overhead was front-loaded.

The Optimized Architecture pays a small startup cost (~150 ms) and then scales linearly: documents flow through Gateway → Index Node → Shard Cluster. Each doubling of dataset size costs about a doubling of indexing time, as it should.

This is the other half of the algorithm-first claim: it isn't only the *search* algorithm that matters, the *indexing pipeline's* algorithm matters too. The Previous Architecture's pipeline has a fixed cost so high that **it disqualifies the architecture from large-scale ingestion** before any search query is run.

---

## 7. What we'd do differently with more time

1. **Push to 1M and 10M documents.** At those scales the algorithm-first ceiling will diverge from the architecture-overhead floor and the Optimized Architecture should pull ahead — visibly. We did not have the wall-clock budget this semester.
2. **Add resource collection.** [benchmarks/run-experiment.js](../../benchmarks/run-experiment.js) already samples CPU and memory via a `withSampler` helper; we ran out of time to wire those into the analyzer.
3. **Co-locate text-node with shard-cluster.** Most of the 45 ms is HTTP hops; some of those hops are *unconditional* (every query asks the schema registry, every query hits the gateway). Caching the schema in the gateway in front of every search would shave ~10 ms off the floor.

---

## 8. The single sentence

**On data scales we could measure, both architectures' search cost is bounded by their algorithm, not by the data size — exactly as the algorithm-first principle predicts. The Previous Architecture is up to 46× faster per query at every measured scale, not because of its algorithm, but because it does not pay the architectural cost of a multi-service pipeline; the Optimized Architecture is the only one that can ingest large datasets in the first place.**

That trade-off — pipeline cost vs distributed scalability — is what [01-why-algorithm-first.md](01-why-algorithm-first.md) called *engineering reality*. The Optimized Architecture is the right design for the **next** order of magnitude of data; the Previous Architecture is the right design for the **current** one. Algorithm choice doesn't make that trade-off go away — but it does guarantee that whichever architecture wins, neither will collapse under more data.
